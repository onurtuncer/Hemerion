\begin{abstract}
Functional Mock-up Interface (FMI) co-simulation is widely used to test
guidance, navigation and control (GNC) software, but the sensor boundary is
usually crossed as idealized floating-point quantities. This bypasses the
code that fails most often on real hardware: the byte-level drivers and
protocol parsers that turn a receiver's UART stream or an inertial part's SPI
registers into engineering units. We present protocol-accurate sensor FMUs,
which take noiseless truth over FMI, apply a grade-specific error model,
quantize to register counts, and emit wire-exact traffic on the bus the
physical part uses, so unmodified firmware parses the bytes it will see in
flight. Because each error model inverts the on-target conversion routine, a
round-trip test pins simulator and flight code together. We instantiate five sensors in one embedded
framework, three of them register-accurate (a synthetic MEMS IMU on SPI, a
Bosch BMP390 and a MEMSIC MMC5983MA on I$^2$C), and exercise four end-to-end against a
verified 6-DoF two-stage-rocket plant. The pattern exposes behaviour a
value-level FMU cannot: a receiver losing its fix to export-control limits
31~s after lift-off, a FIFO with sticky overflow semantics, and a magnetometer
whose bridge offset, comparable to Earth's field, is removed only by a
multi-transaction SET/RESET handshake, without which heading is a median
$34^\circ$ out. Decoded error matches injected error within sampling
uncertainty on every channel, and 20,000 inertial samples cross the SPI bus
with zero checksum errors. The same decoder code runs unchanged in FMI
co-simulation and Renode emulation, and cross-compiles unmodified for the
STM32 flight computer.
\end{abstract}

\section{Introduction}
% ===========================================================================
The Functional Mock-up Interface (FMI)~\cite{fmi2020,blochwitz2011fmi} has
become the lingua franca for coupling heterogeneous simulation tools, and
co-simulation is now routine in the verification of guidance, navigation and
control (GNC) software~\cite{gomes2018cosim}. A typical setup couples a plant
model---vehicle dynamics, environment, actuators---to the control software and
exchanges signals across the FMI boundary as scalar reals: position in metres,
angular rate in radians per second, magnetic field in microtesla.

That convenience hides a validation gap. On real hardware, GNC software does not
receive metres and radians. It receives a stream of bytes from a GNSS receiver's
UART, and the contents of data registers read over SPI or I$^2$C from an
inertial measurement unit (IMU). Between those bytes and the floating-point
quantities a control law consumes sits a substantial, historically bug-prone
body of code: framing and synchronization, checksum validation, little-endian
scaled-integer decoding, register-map sequencing, FIFO management, and
fixed-point-to-SI conversion with a full-scale range the driver---not the wire
format---must know. A value-level sensor FMU that emits clean reals exercises
\emph{none} of it. The software under test in the lab is therefore not the
software that flies.

Hardware-in-the-loop (HIL) rigs close this gap by driving the real buses of a
real flight computer, but they are expensive, poorly parallelizable, and
unavailable early in development. Software-in-the-loop (SIL) co-simulation is
cheap and scales to continuous integration, yet it is exactly where the
value-level shortcut is normally taken.

This paper argues that the shortcut is unnecessary. We introduce
\emph{protocol-accurate sensor FMUs}, a co-simulation pattern in which each
sensor FMU:
\begin{enumerate}
  \item takes noiseless \emph{truth} in over ordinary FMI input variables,
        driven by a physics plant through the importer's connections;
  \item applies a sensor-grade-specific stochastic error model and quantizes
        the result to the physical part's register counts; and
  \item emits \emph{wire-exact} protocol frames---sync bytes, scaled integers,
        checksums---on a channel that stands in for the part's real bus, with
        \emph{no sensor data on FMI output variables}.
\end{enumerate}
The flight software decodes those frames with the \emph{unmodified} on-target
driver and conversion code. The FMI boundary carries physics; the sensor
boundary carries bytes, as on the vehicle.

We make four contributions:
\begin{itemize}
  \item \textbf{The pattern} (Section~\ref{sec:method}): a reusable structure
        for byte-accurate sensor FMUs, including where unit and frame mismatches
        belong (the orchestration layer) and an \emph{inverse-model} property
        that makes the simulator and the flight code mutually self-checking.
  \item \textbf{Talker and polled transports} (Section~\ref{sec:transport}):
        modeling a GNSS receiver as a \emph{talker} that pushes frames, an
        IMU as a \emph{polled} SPI peripheral with a register map and FIFO, and
        two dissimilar I$^2$C parts whose bus conventions differ from each
        other, rather than flattening all of them to pushed byte streams.
  \item \textbf{Behavior a value-level FMU cannot express}
        (Section~\ref{sec:casestudy}): a receiver dynamics envelope (u-blox
        platform models and COCOM export limits) that revokes the fix in flight,
        FIFO-overflow semantics under a slow consumer, and a magnetometer whose
        bring-up \emph{blocks on the plant}---its bridge offset can only be
        measured by taking two real measurements in opposite magnetic
        polarities.
  \item \textbf{End-to-end verification of four sensors}
        (Section~\ref{sec:results}) against a 6-DoF two-stage-rocket plant whose
        trajectory is itself checked against published reference data, showing
        the decoded error equals the injected error within sampling
        uncertainty, that the byte chain crosses three transports without a
        checksum or transfer error, and that the
        register-level conditioning sequence the flight code runs recovers the
        part parameter it is supposed to recover.
\end{itemize}
The pattern is realized in Hemerion, an open-source (GPLv3) C++23 embedded GNC
framework whose modules cross-compile to STM32 firmware and, unchanged, to
x86 shared libraries for co-simulation.

\section{Related Work}
% ===========================================================================
\textbf{FMI co-simulation and signal-level SIL.} FMI~\cite{fmi2020} standardizes
model exchange and co-simulation~\cite{blochwitz2011fmi}, and Gomes et
al.~\cite{gomes2018cosim} survey the field. It is used routinely to run embedded
control software in the loop against physical
models~\cite{pedersen2016fmi,mikelsons2017virtual}. In all of this the sensor
boundary is crossed at the level of physical \emph{quantities}: the plant hands
the control code real-valued positions and rates. PX4's
software-in-the-loop does the same, taking simulated sensor values in SI units
over MAVLink (\code{HIL\_SENSOR}, \code{HIL\_GPS}) or the Gazebo bridge and
writing them to its internal topics~\cite{px4_sim}, so none of its device
drivers runs.

\textbf{Protocol-level sensor simulation inside a flight stack.} ArduPilot's
SITL is the notable exception and the closest prior practice~\cite{ardupilot_sitl}.
Its simulated GNSS receiver generates the wire protocol of a chosen
backend---u-blox UBX, NMEA, SBP, Septentrio SBF, Trimble GSOF or NovAtel---on a
simulated serial port that the unmodified \code{AP\_GPS} driver parses, and a
simulated I$^2$C bus answers the real drivers' transfers with device models
such as an MS5611 barometer, a QMC5883L magnetometer and an ICM-40609 IMU. We
share that premise. The differences are in where the models live and what they
can be coupled to. ArduPilot's device models are part of one flight stack's own
test harness, written against its HAL and driven by its own vehicle model; ours
are standard co-simulation FMUs with no dependency on the consumer, importable
under any FMI master, driven by an external 6-DoF plant through FMI
connections, and reusable unchanged under an instruction-accurate emulator. We
also treat the receiver's dynamics envelope, the FIFO's overflow semantics and
the magnetometer's conditioning state as first-class model behaviour, and we
measure the pattern's transport fidelity rather than only using it.

\textbf{Frames across the FMI boundary.} The closest prior art carries
wire-level frames through FMI itself. FMI 3.0 adds an opaque \code{Binary}
variable type and clocked variables~\cite{junghanns2022fmi3}, motivated in part
by the wish to exchange whole bus frames such as CAN or SOME/IP; building on
this, the FMI Layered Standard for Network Communication
(FMI-LS-BUS)~\cite{fmilsbus2025} standardizes transporting network frames
between FMUs. We differ on three axes. \emph{(i)~Scope}: FMI-LS-BUS targets
inter-ECU \emph{network} buses (CAN/CAN-FD, with LIN/FlexRay/Ethernet in
progress), not \emph{sensor peripherals}; it has no notion of a polled
register-map/FIFO SPI device or a framed GNSS message stream, which is precisely
where sensor driver code lives. \emph{(ii)~Semantics}: it models the transport
medium with a dedicated bus-simulation FMU, whereas our contribution is the
register- and receiver-level behaviour of the part itself---fix revocation under
COCOM/platform limits, FIFO overflow under a slow poll. \emph{(iii)~Interface}:
it exchanges frames as FMI binary \emph{variables} at communication points; we
keep the byte stream off the FMI variable set entirely and emit it on the part's
real bus, so transport granularity is the bus's, not the importer's step.

\textbf{Register-level sensor and virtual-platform emulation.}
Instruction-accurate emulators such as Renode~\cite{renode} run unmodified
firmware against emulated cores and model SPI/I$^2$C sensor peripherals with
register maps, and bus middleware such as Vector SIL Kit~\cite{silkit} can bridge
such virtual platforms. Register-level sensor emulation is therefore not itself
new. What is new here is bringing that fidelity \emph{to the FMI co-simulation
boundary}, co-solved with a continuous 6-DoF plant: the same sensor logic that
answers the firmware's SPI transfers is an FMU wired to the physics. Because the
sensor model is ordinary host code, one FMU can feed a native co-simulation
process or Renode's emulated UART/SPI/I$^2$C unchanged---and the same device
models are reused verbatim by the Renode-hosted software-in-the-loop tests,
rather than being a second implementation that can drift.

\textbf{Same-code SIL.} The strongest validity claim a SIL harness can make is
that it runs the identical object code that will fly. Frameworks that share a
codebase between host simulation and target firmware achieve this for control
logic; we extend it down to the sensor driver and protocol layer, normally
stubbed out in SIL precisely because value-level FMUs make it easy to.

\section{Protocol-Accurate Sensor FMUs}
\label{sec:method}

\subsection{Architecture}
Each sensor is packaged as an FMI 2.0 co-simulation FMU with the structure of
Fig.~\ref{fig:pattern}. Truth enters as real-valued FMI \emph{inputs}, wired by
the importer (the co-simulation master, in FMI 2.0 terms) from a 6-DoF plant. Inside \code{do\_step()} the FMU
applies its error model, quantizes to register counts, frames the counts into
the sensor's wire protocol, and pushes the resulting bytes onto a transport that
stands in for the physical bus. The FMU carries \textbf{no sensor data on FMI
outputs}: to the importer it is a sink, and its observable behavior is the
byte stream, exactly as a real receiver's observable behavior is its UART
traffic. The only FMI outputs any of the sensor FMUs declares are two
diagnostic counters on the BMP390 model---conversions latched, and conversions
produced with the part outside its rated pressure or temperature
envelope---which report something the silicon cannot and change nothing on the
bus.

\subsection{Two fidelity tiers from one pattern}
\label{sec:tiers}
The pattern admits two tiers, and both are instantiated. A \emph{generic} model
represents a class of part---a compass-grade three-axis magnetometer, a MEMS
barometer---with a plausible register sensitivity and a talker transport; it
costs a day to write and exercises the parser and the conversion arithmetic. A
\emph{part-accurate} model transcribes one datasheet: its register map, its bus
conventions, its calibration data, and whatever internal state a driver has to
manage. Two of the five sensors exist at that tier, the Bosch BMP390 and the
MEMSIC MMC5983MA. The SPI IMU sits between the two: it is
\emph{register-accurate} but \emph{synthetic}, a register map, FIFO and shift
register in the shape most MEMS inertial parts share, with sensitivities taken
from a representative part rather than one datasheet transcribed. It exercises
everything a polled peripheral asks of a driver without claiming to be a
particular device, and the paper is careful to call it that. The generic
magnetometer, barometer and radar-altimeter emitters remain, since a scenario
that only needs a field measurement should not pay for a register file. The
interesting claims in this paper come from the register-accurate models, and
Section~\ref{sec:transport} is about what they buy.

\subsection{The shared error model}
\label{sec:errormodel}
With the exception of the GPS receiver (which perturbs at the navigation-fix
level, since a receiver outputs a solution, not counts), every model applies the
same two-term Gaussian error per measurement channel and then quantizes:
\begin{equation}
y[k] = \operatorname{sat}\!\Big(\operatorname{round}\big(
        (x_{\text{truth}}[k] + b + w[k])\, S \big)\Big),
\label{eq:errormodel}
\end{equation}
\[
b \sim \mathcal{N}(0,\sigma_b^2), \qquad w[k] \sim \mathcal{N}(0,\sigma_w^2),
\]
where $b$ is a \emph{turn-on bias} drawn once per run per axis (the constant
offset a real part exhibits after each power-up), $w[k]$ is white measurement
noise drawn per sample, $S$ is the register sensitivity in LSB per physical
unit, and $\operatorname{sat}(\cdot)$ clips at the register's full-scale range
as silicon does rather than wrapping. Setting any $\sigma$ to zero disables that
term cleanly. Every constructor takes an RNG seed (defaulting to
\code{std::random\_device}); seed plus configuration fully determine the output
sequence, including the turn-on biases. Each FMU exposes that seed and every
$\sigma$ as fixed FMI parameters, and the case study derives a distinct stream
per part from one run seed, so that the parts are reproducible without being
correlated with each other. Table~\ref{tab:params} lists the configured error
parameters for the five models, chosen to represent the reference parts of
Table~\ref{tab:sensors}.

Several further terms are implemented and are off by default. On the IMU the
bias can wander as a random walk whose increment scales with
$\sqrt{\Delta t}$, and a per-axis scale-factor error and a small-angle
misalignment of the triad are drawn once per run; the magnetometer adds a
symmetric soft-iron matrix; the receiver adds a first-order Gauss--Markov error
to each position and velocity channel, with a reported accuracy that can be
made optimistic, and a processing latency between closing an epoch and
delivering its solution; and each stamped part can be given its own clock, with
a rate error drawn once per run and a per-sample jitter. A disabled term draws
nothing from the random stream, so enabling one does not move an existing
seeded run. The case study leaves all of them at zero: its claims concern the
transport, and these terms matter to a navigation filter rather than to a
driver.

\subsection{What a part-accurate model adds to
\texorpdfstring{\eqref{eq:errormodel}}{the shared form}}
\label{sec:partmodels}
Equation~\eqref{eq:errormodel} describes a \emph{channel}. A part has more than
a channel, and the two register-accurate I$^2$C models differ from the generic
form in opposite directions.

The BMP390's raw output means nothing on its own: the part ships 24-bit
uncompensated words that only become pascals after the floating-point
compensation polynomial of the datasheet's section~8.4~\cite{bosch_bmp390},
evaluated with
coefficients burned into each individual part's NVM at the factory. A model that
emitted counts proportional to pressure would produce a stream the real driver
would decode into the wrong number. The FMU therefore takes the static
pressure and temperature of the air the part is in---the plant's own, where the
plant publishes them, and the ICAO standard atmosphere at truth altitude
otherwise---and \emph{numerically inverts the real
compensation polynomial}---a bisection on the monotone forward map---to find the
raw words a physical part would have converted, and serves the calibration
coefficients as the 21 NVM bytes the driver reads at bring-up. Agreement in
Section~\ref{sec:results} is therefore agreement between two executions of the
same published arithmetic across a register interface, not between a model and
its own inverse.

The MMC5983MA~\cite{memsic_mmc5983ma} needs no compensation at
all---sensitivity is a fixed $16384$~counts/gauss with no per-part NVM---and
the fidelity has to go somewhere
else, into \emph{state}. Its sensing elements are Wheatstone bridges of
anisotropic magneto-resistive film, and an on-die coil re-magnetizes them in
either direction. After a SET the applied field enters the bridges positively;
after a RESET, negatively. The bridge's own electrical offset, being electrical
and not magnetic, does not follow:
\begin{align}
\text{after SET}\quad   y_+ &= n + HS + \delta,\nonumber\\
\text{after RESET}\quad y_- &= n - HS + \delta,\label{eq:setreset}\\
\Rightarrow\quad HS &= \tfrac{1}{2}(y_+ - y_-), \quad
\delta = \tfrac{1}{2}(y_+ + y_-) - n,\nonumber
\end{align}
with $n$ the part's null-field output ($131072$ counts, mid-scale, not zero).
The measurement model therefore applies the sensing polarity to the
\emph{field} and not to $\delta$, which is what makes~\eqref{eq:setreset}
recoverable by a driver and unrecoverable by one that never runs the pair. It
also distinguishes two offsets that a value-level model would merge: $\delta$,
which SET/RESET removes, and a per-run \emph{hard-iron} vector, which is a real
field the installation adds and which no coil pulse removes. $\delta$ is drawn
each run from the datasheet's $\pm0.5$~gauss null-field tolerance taken as a
$3\sigma$ bound---i.e.\ $16.7$~\textmu T $1\sigma$, deliberately the same order
as Earth's entire field, so that a driver which skips the conditioning sequence
is wrong by roughly $100\%$ rather than by a rounding error.

\subsection{The inverse-model property}
\label{sec:inverse}
The sensitivity $S$ in~\eqref{eq:errormodel} is \emph{the same constant} the
consuming driver passes to \code{convert\_raw\_to\_si()}. Scale is configuration
both ends share---exactly as on real silicon, where the full-scale range is a
register the driver wrote, not a field on the wire. Consequently the on-target
conversion is the algebraic inverse of the FMU's quantization step: feeding the
emitted counts back through \code{convert\_raw\_to\_si()} recovers the noisy SI
sample to within quantization error. A round-trip unit test that feeds each
emitter's output through the real parser therefore pins the simulator and the
flight code to one another; if either drifts, the test fails. This mutual
self-checking is a direct benefit of keeping scale off the wire.

\subsection{The wire protocol}
Not every sensor boundary is framed, and the pattern does not force one. The
two register-accurate I$^2$C parts have \emph{no} wire protocol above the bus:
what crosses is a register burst---seven bytes of packed 18-bit field words, or
a shadowed pressure/temperature/\code{SENSORTIME} block---exactly as on silicon,
and the ``parser'' on the flight-software side is the datasheet's bit unpacking.
Where a frame \emph{is} the part's real interface, it is wire-exact: the GPS FMU
speaks real u-blox UBX. The generic-tier emitters and the IMU's FIFO share a
minimal binary framing that intentionally mirrors UBX so that each parser
mirrors the proven UBX parser's structure:

Each sensor uses \emph{distinct} sync bytes (IMU \code{A5 5A}, baro \code{B7
7B}, radalt \code{C9 9C}, mag \code{D1 1D}, vs.\ UBX's \code{B5 62}), so an
interleaved multi-sensor stream can never desynchronize one parser into
another's frames. Unknown message ids are checksummed and skipped, not buffered,
so a stream carrying future message types cannot desync today's parser.

\subsection{Orchestration: adaptation belongs to the importer}
\label{sec:orchestration}
Unit and frame mismatches are resolved in the co-simulation orchestration layer,
not inside the models, and the fewer there are the better: a port that carries
its unit in its name can be connected without a conversion to get wrong. In the
case study the plant publishes geodetic position in degrees, NED velocity, body
rates, body-frame specific force (aerodynamic plus thrust force over mass at
the centre of gravity, gravitation excluded) and its own static pressure, and
each of these connects one-to-one to the sensor input of the same quantity. The
receiver derives speed-over-ground and course from the NED velocity itself. One
unit conversion remains and rides on the connection as a modifier: air
temperature, published in kelvin, into the barometer's and the magnetometer's
Celsius inputs.

One quantity has no plant output and is a function of several. The body-frame
\emph{magnetic field} depends both on where the vehicle is and on how it is
pointing: the host evaluates the World Magnetic Model
(WMM2025, to degree and order 12) at the plant's latitude, longitude and
altitude for a fixed date, and rotates the result into body axes with the
plant's yaw, pitch and roll. Because a connection modifier sees only a single
source variable, the host computes this after each step and writes the
magnetometer's inputs through importer \emph{properties}, incurring the same
one-step transport delay a connection would. Keeping these adaptations in the
importer leaves every model free of scenario-specific glue and reusable across
vehicles.

\section{Talker and Polled Transports}
\label{sec:transport}
% ===========================================================================
A central design choice is that not all sensors are pushed byte streams.
Table~\ref{tab:sensors} lists the five instantiated models across three
transport classes. A \emph{talker}---a receiver or sensor that emits frames
whenever it has them---sends its bytes over UDP, standing in for a UART RX line
(or Renode's emulated one). The environment supplies each talker's destination
(\code{HEMERION\_$\langle$SENSOR$\rangle$\_FMU\_UDP\_*}), keeping every model
free of FMI String variables and letting a launch script retarget a stream
without repackaging the archive. A \emph{polled} part sends nothing: it holds
state until the flight computer comes to get it, over shared-memory SPI or
I$^2$C buses that carry one framed transaction per handshake.

The split matters: \emph{the receiver talks, the other three are polled}.
A GNSS module pushes navigation solutions down a UART whenever it has them; an
inertial part sits holding samples until the flight computer asserts
chip-select, and a barometer or magnetometer converts nothing at all until a
control register says so. Modeling all of them as pushed byte streams would
exercise the packet parsers and nothing else---no register map, no FIFO, no
chip-select, no ODR register, no conditioning handshake, none of the sequence
firmware actually runs against such a part.

\subsection{The IMU as an SPI peripheral}
The design splits along the boundaries a real system has:
\begin{itemize}
  \item \textbf{the datasheet} (\code{ImuSpiSlave}): register file, sample FIFO,
        shift register; names no transport, so it can be unit-tested against the
        real on-target driver with nothing in between;
  \item \textbf{the board} (\code{sim/spi\_shm}): one named shared-memory region
        per bus carrying chip-select-framed transfers between two processes,
        plus an endpoint that puts any device model on a bus;
  \item \textbf{the controller} (\code{ImuSpiDriver}): \emph{on-target code}
        that probes \code{WHO\_AM\_I}, samples the data-ready line, reads
        \code{STATUS}/\code{FIFO\_COUNT}, and bursts the FIFO port.
\end{itemize}
The register map is the shape most MEMS parts share (Table~\ref{tab:regmap}).
Every transfer opens with a command byte---bit~7 read/write, bits~6..0
address---during which the part shifts out a don't-care exactly as silicon does
while that byte is still arriving; successive bytes walk up the map, which is
what lets \code{STATUS} and both \code{FIFO\_COUNT} bytes emerge from one
four-byte transfer. One shared-memory handshake is one transfer, which is the
granularity a \code{HAL\_SPI\_TransmitReceive} call has on the target. The FIFO
holds \emph{complete} frames---the identical bytes the FMU would have put on a
UDP socket---so a controller that falls behind loses whole \emph{samples}, never
framing, and is told through the sticky overflow bit. The only piece that
differs between host co-simulation, Renode and the STM32 is the bus
implementation beneath the driver: a chip-select-framed transfer and a data-ready
read.

\subsection{Two I\texorpdfstring{$^2$}{2}C parts with differing bus conventions}
\label{sec:i2c}
The barometer and the magnetometer are also polled, but over I$^2$C, and
carrying them at the part-accurate tier surfaces something the SPI model alone
does not: \emph{two devices on the same bus family do not obey the same rules},
and a driver that assumes one part's convention on the other corrupts its
configuration silently. Both device models are written from their datasheets and
they differ where the datasheets differ.

The BMP390's multi-byte writes are register/data \emph{pairs}: each written
value is preceded by its own address. The MMC5983MA's are not---the byte after
the address in write mode sets a register pointer, and both further writes
\emph{and} reads auto-increment from it. The MMC5983MA's four
\code{Internal control} registers are marked write-only in the datasheet and
duly read back as zero on the model, so a driver doing read-modify-write on one
of them reads zero and clobbers every bit it meant to preserve, on the model
exactly as on the part. (This is why the on-target driver shadows
\code{Internal control 0} instead.) Its trigger bits (take-measurement,
take-temperature, SET, RESET, OTP-read) are self-clearing at the write, while
the interrupt-enable and automatic-set/reset bits persist; its status flags are
set when a measurement lands and cleared by writing them back as ones. None of
this is incidental: it is the content of the statement that the driver is correct.

The magnetometer model additionally carries the one piece of state a register
file cannot express: the magnetization sign left behind by the last coil pulse
(Section~\ref{sec:partmodels}). A measurement taken after a RESET really comes
back negated, so a driver that forgets to leave the part SET really reads a
sign-flipped field. Because the part's automatic set/reset bit differences its
own pair internally, the model treats the hardware and software mechanisms as
\emph{alternatives}: with automatic set/reset on, the result is
positive-polarity and already offset-free, and a manual pair would measure the
standing field and store it as an offset---so the driver refuses the call rather
than performing it. Running both is not redundancy, it is a bug, and the
simulator is where that is cheap to discover.

One transport limitation applies: the shared-memory I$^2$C bus carries
one peripheral per bus, so the BMP390 and the MMC5983MA sit on two separate
simulated buses here, where a real board would put both on I2C1 at \code{0x76}
and \code{0x30}. Multi-drop addressing is the one thing about driving two
I$^2$C parts that this work does not exercise.

\section{Case Study: A Two-Stage Rocket to Orbit}
\label{sec:casestudy}
% ===========================================================================
We exercise the pattern with an end-to-end scenario coupling six independently
developed pieces under the Ecos importer~\cite{ecos} (which imports
FMUs through fmi4c~\cite{fmi4c}): a 6-DoF plant, the GPS, IMU, BMP390 and
MMC5983MA FMUs, and a host stand-in for the STM32H743 flight computer's
sensor-ingest paths, which drives all four buses with the unmodified on-target
drivers. The importer runs a fixed 0.1\,s communication step (a 10\,Hz GNSS
navigation rate; the IMU latches at 100\,Hz within each step) over Scenario 17's
200\,s window. Neither I$^2$C part has a rate parameter at all: each converts at
whatever the flight computer programs into its control registers, and neither
converts anything while it is still in the power-on state its own datasheet
specifies.

\subsection{Execution model and synchronization}
\label{sec:sync}
% Drafted from examples/rocket_gps_ecos/{cosim_host_main,flight_computer_main}.cpp,
% the sensor fmu_main.cpp files, sim/{spi,i2c}_shm and Ecos'
% fixed_step_algorithm.cpp / simulation.cpp.
The scenario runs as two operating-system processes, and only one of them is
under the importer's control. The importer process hosts the five FMUs and
advances them with Ecos's fixed-step algorithm at $h=0.1$\,s. The
flight-computer stand-in is a separate process: it is not an FMU, it is never
stepped, and it has no access to simulated time. It reaches the sensor FMUs
only through the three buses. This subsection states what that arrangement does
and does not synchronize, because the sample counts and the timing behaviour
reported in Section~\ref{sec:results} follow from it.

\emph{Stepping order.} At each communication point $t_n$ the importer visits the
FMUs sequentially, in the order they were registered; for each it applies the
pending inputs, calls \code{doStep}$(t_n,h)$ and reads the outputs. Only after
all five have stepped are the connections transferred. No FMU therefore sees an
output that another produced in the same step: the scheme is of Jacobi type,
each sensor FMU advances over $[t_n,t_{n+1}]$ against plant truth sampled at
$t_n$ and held, and every connection carries one communication step of delay.
Quantities the host derives from several plant outputs
(Section~\ref{sec:orchestration}) are written after the step and carry the same
delay. The plant takes one implicit Radau step per communication step.

\emph{Inside a step.} Simulated time advances only inside \code{doStep}, and
each part does a whole step's worth of sampling there
(Table~\ref{tab:sync}). The receiver emits one frame, stamped $t_{n+1}$. The
IMU latches $\operatorname{round}(h f_s)=10$ samples into its FIFO, each with a
fresh noise draw and its own time stamp $t_n+k/f_s$. The two I$^2$C parts
free-run at the period their control registers currently select: every whole
period that elapses within the step latches a conversion and the remainder
carries into the next step, so a 50\,Hz part stepped at 10\,Hz does convert at
50\,Hz. Its data registers hold one conversion, however, so only the newest of
a step's five is ever visible to a controller. A one-shot measurement that the
firmware triggers over the bus is served by the next \code{doStep}.

\emph{Bus service.} Bus traffic is not tied to communication points. Each
shared-memory bus is answered by its own service thread inside the importer
process, at whatever wall-clock instant the controller posts a transaction, and
the receiver's datagrams are queued by the operating system. A device model's
state is guarded by one mutex held for the whole transaction---a
chip-select frame on SPI, START to STOP on I$^2$C---so a read never observes a
half-latched sample and a latch never lands inside a transaction.

\emph{The consumer.} The flight-computer process runs a free loop on the host's
monotonic clock: it waits up to 5\,ms for a datagram and drains the socket,
bursts the IMU FIFO for as long as data-ready is asserted, then polls the
barometer and the magnetometer. The drivers are the unmodified on-target ones,
but their scheduling is the host operating system's and not the target RTOS's:
task periods and interrupt latency are not represented in this tier, and are
the business of the instruction-accurate one (Section~\ref{sec:discussion}).

\emph{Three clocks.} A run therefore has three time bases: simulated time; each
part's own clock, which stamps the IMU frames and drives the BMP390's
\code{SENSORTIME} counter (and is ideal here, the clock-error terms of
Section~\ref{sec:errormodel} being off); and the flight computer's clock, which records
arrival. Two parts give the firmware no stamp at all. A NAV-PVT frame carries no
time the parser reads, so a fix is placed by its epoch index; an MMC5983MA
sample carries nothing, so it is aligned to the most recent IMU stamp, as
firmware does with an unstamped sensor. Arrival time equals simulated time only
when the importer is paced at a real-time factor of one. \emph{Sample-time}
fidelity is thus carried by the parts' own stamps and is exact to the sample
period; \emph{arrival-time} fidelity is bounded by $h$, because a step's samples
all become visible at once.

\emph{Pacing.} The importer can sleep after each step until wall-clock time
$t/\rho$ for a real-time factor $\rho$. Unpaced, the run executes several times
faster than real time, and not uniformly: powered flight in the atmosphere is
expensive to integrate and coasting is cheap. Three consequences follow. First, an unpaced importer can outrun the consumer's poll
loop and overflow the IMU FIFO (Section~\ref{sec:fifo}); paced at $\rho=1$ the
stream is lossless. Second, an unbuffered part is observable at no more than
the smallest of its programmed rate, $1/h$ and the consumer's poll rate,
whatever the pacing. Third, the magnetometer's bring-up blocks on the importer:
a triggered measurement lands only at the next \code{doStep}, and the driver
polls for 200\,ms before timing out, so a communication step must take less
wall-clock time than that or the probe is retried
(Section~\ref{sec:magcond}).
The run reported in Section~\ref{sec:results} is paced at $\rho=1$ and seeded,
unless stated otherwise.

\emph{Start-up and shutdown.} Either process may start first. The flight
computer binds its UDP port, so that early datagrams queue rather than drop,
and then waits for the three buses to appear. Frames the IMU buffered before
the controller's probe reset the FIFO are discarded, which is the origin of the
ten samples missing in Section~\ref{sec:integrity}. At termination the IMU FMU
keeps its bus up for up to 2\,s while the FIFO drains and then powers the part
down; the flight computer treats a vanished peripheral as the end of the run
rather than as a bus fault, drains the socket and exits.

\emph{Determinism.} The loop is open: nothing the flight computer computes
returns to the plant, so the trajectory is independent of the consumer's
timing. With a fixed seed, each part's error stream is a function of simulated
time: Section~\ref{sec:fifo} repeats the reference run at a different pacing
and finds every sample common to both identical. The coupled run is nevertheless not
reproducible sample for sample. Which conversion of an unbuffered part the
consumer observes, where a FIFO burst boundary falls, and the instant at which
the firmware programs a polled part's rate registers all depend on host
scheduling. Statistics reproduce; a byte-wise comparison of the consumer's logs
does not. Removing that residue means stepping the consumer on the importer's
clock, as an FMU or as a bus-synchronized process, which is also the
precondition for closing the control loop and is left to future work.

\subsection{Plant verification}
The truth source is a two-stage-rocket FMU (NASA TM-2015-218675 Scenario
17~\cite{nasa_tm2015}: DAVE-ML~\cite{jackson2011daveml} aero/propulsion/inertia
tables, J2 gravity, stage separation) integrated with a Radau IIA scheme on
SE(3). None of the sensor results mean anything if the truth is flying the wrong
mission---and a plant with the wrong staging profile still produces perfectly
clean-looking sensor streams, which is what makes such an error easy to miss.
The run is therefore checked against the three published reference trajectories
for the scenario (Fig.~\ref{fig:envelope}). The criterion is their
\emph{envelope}, not any single one:
they are independent simulators of the same case and disagree by up to $7\%$
(16.97\,km) at $t=200$\,s. Our run lies within the envelope, to a tolerance of
$1\%$ plus 100\,m, at all 2001 samples: it is within 20\,m of all three
references at stage-1 burnout (26.77\,km against 26.75--26.76\,km), sits
0.2--0.3\,km above them at stage-2 ignition (138.52\,km against
138.24--138.34\,km) and lies between them at stage-2 burnout (220.15\,km against
217.97--230.00\,km). This check caught the
scenario's worst defect---an FMU parameter (\code{stg2.ignition\_time\_s})
defaulting to zero flew continuous thrust to 638\,km against a reference topping
out near 251\,km, while every sensor figure still looked plausible.

\subsection{Receiver fix revocation under dynamics limits}
\label{sec:cocom}
A real receiver does not keep reporting a solution however hard the vehicle
accelerates, and a launch vehicle is exactly where that matters. The GPS FMU
gates every fix through two independent mechanisms of real hardware:
\begin{itemize}
  \item \textbf{Navigation-engine platform models} (u-blox \code{dynModel}):
        the receiver rejects a solution outside the configured platform's
        altitude/velocity/acceleration limits. This is a \emph{configuration}
        choice---a register a firmware engineer writes.
  \item \textbf{COCOM export limits}: independently, navigation output stops
        when altitude \emph{and} speed both exceed 18{,}000\,m and 515\,m/s.
        This is an AND (so a high slow balloon and a fast low sled both keep
        their fix, a sounding rocket does not) and it is in every receiver one
        can buy---not a configuration choice.
\end{itemize}
Both are evaluated against \emph{truth}, since it is the vehicle's real motion
that breaks carrier tracking, not the receiver's estimate of it. The example
isolates COCOM (platform model disabled) because it is the more instructive of
the two: enabling the airborne-$4$g model instead trips its acceleration limit
on the \emph{second} epoch (thrust alone is ${\sim}54$\,m/s$^2$, ${\sim}4.6$g),
yielding one usable fix in 2001 and letting COCOM never be the reason for
anything. When a limit is active the receiver still emits one NAV-PVT frame per
epoch---fix type drops to no-fix, satellites to zero, accuracies inflate---and
the flight software gates on fix type, exactly as it must on the vehicle. This
is behavior a value-level FMU structurally cannot present: there is no clean
real to withhold.

\subsection{IMU access over SPI}
The flight computer runs the on-target \code{ImuSpiDriver} against the simulated
part: \code{probe()} (\code{WHO\_AM\_I}, then enable/reset the FIFO), then poll
while the data-ready line is asserted, reading \code{STATUS}+\code{FIFO\_COUNT}
in one transfer and bursting the FIFO. The 16\,KiB FIFO holds roughly 420 frames
($\sim$4\,s at 100\,Hz); a controller slower than that loses whole samples and
learns so from the sticky overflow bit. This is the FIFO's purpose made
observable, and it is testable in isolation: a unit test runs the real driver
against the real device model and asserts the bytes burst from the FIFO are the
bytes the emitter produced---including the normal case where a burst lands
mid-frame, since a controller cannot align its reads to frame boundaries.

\subsection{Magnetometer conditioning over I\texorpdfstring{$^2$}{2}C}
\label{sec:magcond}
The magnetometer is the only sensor in the scenario whose bring-up
\emph{blocks on the plant}, and that is what makes it worth carrying. The other
three parts are configured and then read. The MMC5983MA has to be
\emph{conditioned} first, and conditioning it means taking real measurements:
by~\eqref{eq:setreset} the bridge offset $\delta$ is only separable from the
field by measuring the same field in both magnetic polarities. So
\code{calibrate\_offset()} is a five-step handshake---leave continuous mode,
SET and measure, RESET and measure, average, re-SET, restore continuous
mode---and every step is a separate I$^2$C transaction with a status poll loop
between. It cannot be folded into a register write, and it cannot complete at
all unless the co-simulation is \emph{stepping}, because the simulated part only
converts when the importer advances it.

Three consequences follow, and all three are properties of the real system that
a value-level FMU has nowhere to put.

\emph{Start order stops being free.} The other probes need only the bus to
exist; this one needs the physics to be running. The flight computer therefore
retries the magnetometer probe on a measurement timeout rather than failing, and
distinguishes ``not being stepped'' from ``wrong part'' in its diagnostics---an
artifact of co-simulation that a real board never needs.

\emph{The final SET is not decoration.} Leaving the part RESET yields readings
that are offset-corrected, of the correct magnitude, and negated on every axis.
That is the failure this harness is best placed to catch, because a sign-flipped
magnetometer looks entirely healthy in a summary line and only reveals itself in
a heading.

\emph{Conditioning does not remove everything.} The per-run hard-iron vector
survives it by construction, since it is a real field. The model draws both and
exposes each separately, so a test can attribute a residual to the installation
rather than mistake it for a driver bug---and Fig.~\ref{fig:magfield} shows the
residual as the constant gap it is.

\subsection{Transport integrity across the byte chain}
\label{sec:integrity}
The mission profile reads straight off the decoded IMU stream
(Fig.~\ref{fig:sf}), the cheapest sanity check on the plant there is:
54\,m/s$^2$ at lift-off rising to 125\,m/s$^2$ as stage 1 burns off; a coast of
94\,s that opens at $-1.7$\,m/s$^2$ of residual drag and decays to zero as the
air thins (an accelerometer does not sense gravity); 51\,m/s$^2$ when stage 2
lights, 265\,m/s$^2$ at burnout, then zero.

Table~\ref{tab:transport} gives the transport counts. All 2001 NAV-PVT frames
were decoded, and $20{,}000$ of the $20{,}010$ inertial samples; no checksum
failed, no FIFO overflowed and no transfer or transaction failed on any of the
three buses. The ten absent inertial samples are those the FMU buffered before
the flight computer probed and reset the FIFO---a driver clearing what
accumulated before it took over. Within what the consumer collected, the chain
from 6-DoF truth through four noise models, four encoders, three transports and
the on-target drivers is lossless and wire-correct. Fig.~\ref{fig:rates} shows
the same fidelity in the gyro channel, where the visible LSB banding is the
quantization the flight software must live with on the real part.

\subsection{BMP390: compensated pressure and the range floor}
The BMP390 channel (Fig.~\ref{fig:baroalt}) is the complement to the GPS
result, and it fails for an unrelated reason. Compensated pressure decoded by
the on-target driver follows the plant's atmosphere down from 101.2\,kPa on the
pad until the vehicle passes 16\,km at $t\approx30$\,s, where the reference
part's ADC bottoms out. Inverted through the standard atmosphere, as flight
software does with a static-pressure measurement, the altimeter tracks truth to
$\sim$16\,km and then saturates while the vehicle climbs another 220\,km. Below
15\,km the decoded pressure altitude differs from truth altitude by $-0.4$\,m in
the mean with a standard deviation of 5.3\,m over 144 conversions, a figure
that includes the part's injected noise and turn-on bias.

The floor itself is not a constant, and that is a detail only a register-level
model produces. What saturates is the raw pressure word; the temperature word
does not, and the compensated pressure is a polynomial in both. So the decoded
``floor'' reads 10.44\,kPa while the die is at $-56\,^\circ$C, falls to
9.93\,kPa as the air warms towards the stratopause, and settles at 11.82\,kPa
at $-84\,^\circ$C above it. The die is by then far below the part's
$-40\,^\circ$C rating as well as below its 300\,hPa pressure rating; the words
on the bus stay plausible throughout, as they do on silicon, and the FMU's
diagnostic counter is the only place the excursion is recorded.

The agreement below the range floor is the load-bearing part. The FMU produced
those raw words by \emph{inverting} the Bosch compensation polynomial and the
driver recovered pascals by running it \emph{forward}, with the coefficients
travelling across the bus as the 21 NVM bytes a physical part serves. A
value-level barometer FMU would have agreed with itself; this one agrees with an
independent execution of the manufacturer's published arithmetic, over a
register interface, and the range floor it inherits is the reference part's
rather than a modelling choice.

\subsection{MMC5983MA: bridge-offset conditioning}
\label{sec:magresults}
The magnetometer is where a register-accurate model shows its value most clearly.
On the run reported here the simulated part was born with a bridge offset of
$-7945/{+}80/{+}2688$~LSB, i.e.\ $-48.5/{+}0.5/{+}16.4$~\textmu T, against a
field of 32~\textmu T. The on-target driver's SET/RESET pair measured it at
bring-up and removed it, and every sample afterwards is a field rather than a
field plus an unknown vector larger than itself. Over the flight the decoded
field magnitude ran from 31.6 down to 27.3~\textmu T against a truth of 31.8
down to 28.2~\textmu T, as the vehicle climbed to 236\,km and travelled some
540\,km east.

Fig.~\ref{fig:magfield} plots the three body axes rather than the magnitude,
deliberately. The axes are doing three different things. Body $Y$ carries the
horizontal field, $-27$\,\textmu T, because the vehicle heads east across a
field that points north. The field at this site also has an upward component of
16\,\textmu T (the inclination is $-30^\circ$), which the pitch angle divides
between $X$ and $Z$; $X$ falls from $+12$ to $+2$\,\textmu T as the vehicle
pitches over. That geometry is exactly what a swapped axis or a sign error
destroys and exactly what a magnitude plot hides. The constant gap between
decoded samples and the truth handed to the FMU, $+1.2/{+}0.5/{+}1.4$\,\textmu T,
is the simulated installation's hard iron, present by design and not removed by
conditioning; it is also why the decoded magnitude sits below truth.

Fig.~\ref{fig:magerror} quantifies what skipping the conditioning would have
cost, drawn from the same samples with the measured bridge offset added back:
$74$--$83^\circ$ of direction error on this run. This draw is a large one, an
offset magnitude of 51\,\textmu T that the model's distribution exceeds in
$2.4\%$ of draws, so the figure for a single run should not be read as typical.
Sampling $\delta$ from that distribution against a 30\,\textmu T field gives a
median direction error of $34^\circ$, with $9^\circ$ and $83^\circ$ as the 5th
and 95th percentiles, and more than $10^\circ$ in $94\%$ of draws. Heading is
what a magnetometer is for, so the angle is the relevant measure of the damage.
Magnitude is a less reliable witness: on this run an unconditioned driver would
have reported 45--52\,\textmu T, which is visibly wrong, but in $14\%$ of draws
the offset changes the magnitude by less than a tenth while still turning the
vector. This is the sharpest instance of the paper's central claim. Firmware
that never runs the SET/RESET sequence produces a well-formed field stream,
passes every value-level check, and is typically wrong by tens of degrees; no
idealized sensor FMU can present that failure, because there is no bridge in a
floating-point number.

\subsection{Injected driver faults}
\label{sec:faults}
The claim that a value-level FMU cannot present these failures is best tested
by committing them. The flight-computer harness can inject three mistakes a
real driver makes against a real part, each from outside the on-target code:
converting counts with the sensitivities of a different full-scale range than
the part is configured for (\code{imu-range}: $\pm250\,^\circ$/s and
$\pm16$\,g against the part's $\pm2000\,^\circ$/s and $\pm40$\,g); never
running the SET/RESET pair (\code{mag-skip-conditioning}); and conditioning
the part correctly but then leaving it magnetised in the RESET direction
(\code{mag-leave-reset}), which a second code path on a real board can do
behind the driver's back. Each was run against the reference scenario with the
same seed, so the parts produced the same samples as in
Section~\ref{sec:integrity}; Table~\ref{tab:faults} gives the result.

quiet one, a constant factor that a filter will happily absorb into its
estimate; the conditioning faults are the loud ones, tens of degrees of
heading or a reversed field, and they are the two the Renode
software-in-the-loop test of Section~\ref{sec:discussion} also guards.

\section{Discussion}
\label{sec:discussion}
% ===========================================================================
\textbf{Same code across three tiers.} The decoders exercised above are the
identical translation units that run inside Renode's instruction-accurate STM32
simulation and that the STM32H743 firmware cross-compiles; only the bus shim beneath the
driver changes (UDP or shared memory here, \code{HAL\_SPI\_TransmitReceive} or
\code{HAL\_I2C\_Mem\_Read} plus GPIO on the target). For the two I$^2$C parts
this is measured rather than asserted: two software-in-the-loop tests gate in
continuous integration, each running the cross-compiled H743 firmware inside
Renode, through Renode's emulated I$^2$C controller, a C\# bridge peripheral, a
TCP hop and the shared-memory bus, against the same \code{Bmp390I2cSlave} and
\code{Mmc5983maI2cSlave} the FMUs embed. The magnetometer loop exercises the
full blocking SET/RESET handshake over that transport, and its load-bearing
assertion is not the field values but that the bridge offset the firmware
reports matches, to one LSB, the one the peripheral independently reports having
been born with---the one comparison that separates conditioned firmware from
firmware that merely prints plausible numbers. SIL results are therefore
positioned to transfer to HIL with a validity a value-level harness cannot claim, because the
code that most often breaks on hardware is the code SIL usually omits.

\textbf{The open loop, and what it does and does not cost.} The consumer in
the case study is not stepped by the importer and feeds nothing back to the
plant (Section~\ref{sec:sync}). A co-simulation referee is right to ask what
that gives up. For the claims made here, little: every result in
Section~\ref{sec:results} is a property of the byte path between a part and its
driver, and each part's output is a function of simulated time alone, which the
paced and unpaced runs demonstrate by producing identical samples at identical
stamps. Consumer timing decides which samples are collected, not what they
contain, and the FIFO's and the datagram queue's loss behaviour under an
unpaced importer is the behaviour of those mechanisms rather than an artifact
of the model. What the open loop does cost is twofold. Timing claims about the
firmware---latency from sample to use, jitter, the interaction of several
drivers on one core---cannot be made in this tier, because the consumer's
scheduling is the host's; that is the instruction-accurate tier's job. And
closing a guidance loop through these FMUs would require the consumer to be a
stepped participant, so that an actuator command computed from a sample reaches
the plant at a defined simulated time. The pattern does not prevent that: a
flight-computer FMU that owns the three bus controllers and advances them in
its own \code{doStep} is the natural construction, and it is the next step of
this work.

\textbf{Cost.} Protocol accuracy is cheap at the importer. Unpaced, with no
consumer attached, the importer advances the plant and all four sensor FMUs
through the 200\,s scenario in 21.1\,s of wall-clock time on the development
machine; attaching the consumer, whose bus transactions are answered by the
FMUs' service threads, raises that to 23.7\,s. Raising the IMU's rate tenfold,
to 1\,kHz, changes it by less than the run-to-run variation. The plant's
implicit integration dominates, and the sensor models' noise draws,
quantization, framing and register bookkeeping are a small fraction of a step.

\textbf{Conformance as a side effect.} Because neither sensor FMU hand-writes
the FMI export table---a \code{fmu4cpp}~\cite{fmu4cpp} layer exports the full
table and the model description is \emph{generated} from the registered
variables---the description and binary cannot drift, and the archive passes a
strict loader (fmi4c resolves the complete 2.0 table up front and refuses a
binary that omits any function, even those whose capability flags are false).
Generating the description from the model is good conformance pressure any strict
importer would exact.

Generation removes one class of drift but not another. An \code{.fmu} is a zip
whose \emph{root} must hold \code{modelDescription.xml} with \code{binaries/}
beside it, and that layout is produced by the build, not by the model, so a
conformant model can still be sealed into an archive no importer will open. The
build therefore registers a packaging test per exported model per FMI version
(fourteen in the current tree) that unzips the archive and asserts the
description at its root, a binary named for the \code{modelIdentifier} under
\code{binaries/}, and a description declaring that same identifier.

\textbf{Limitations.} The case study exercises the default error models:
per-axis Gaussian noise, a turn-on bias and quantization. The correlated,
signal-proportional and clock terms of Section~\ref{sec:errormodel} are
implemented but not exercised here, and the temperature dependence of bias and
scale is not modelled at all. The magnetic environment is the WMM2025 main field
at a fixed date, with no crustal or time-varying external contribution. The
MMC5983MA's self-test coil applies a field of the model's choosing
(100\,\textmu T), because the datasheet specifies a pass threshold and not the
field the coil produces: a driver self-test exercises the real sequence against
a model that answers, but its absolute threshold cannot be calibrated against
the FMU. The shared-memory I$^2$C bus carries one peripheral per bus, so multi-drop
addressing is not exercised (Section~\ref{sec:i2c}). The radar altimeter is the
one sensor of the five with a model but no case-study run: the scenario is a
launch to orbit, and there is no ground under it to measure. The consumer is a
free-running host process rather than a stepped participant
(Section~\ref{sec:sync}): the loop is open, firmware task timing is not
represented in this tier, every connection carries one communication step of
transport delay, and arrival-time fidelity is bounded by that step. None of
these affect the
paper's claim, which is about the \emph{transport and protocol} fidelity of the
sensor boundary, not the richness of the stochastic model behind it; richer
error models drop into~\eqref{eq:errormodel} without changing the pattern.

\section{Conclusion}
% ===========================================================================
Value-level sensor FMUs let SIL co-simulation test everything about GNC software
except the byte-level driver and protocol code that fails most on real hardware.
We showed that this shortcut is avoidable: protocol-accurate sensor FMUs take
truth in over FMI and answer the part's real bus---wire-exact frames where the
part frames, register bursts where it does not---with no sensor data on FMI
outputs, so the
unmodified flight-software decoder is exercised against exactly what it will see
in flight. The pattern captures a talker/polled distinction across three
transports and in-flight behaviors a value-level model cannot express: a
receiver revoking its fix to export limits, a FIFO overflowing under a slow
consumer, a compensation polynomial that must be inverted before a barometer's
counts mean anything, and a magnetometer with no useful output at all until a
blocking multi-transaction handshake has separated its bridge offset from the
field. Its inverse-model property makes simulator and flight code mutually
self-checking. End-to-end against a verified two-stage-rocket plant, four
sensors decode without a checksum or transfer error across three transports,
the decoded error equals the injected error within sampling uncertainty, and
the conditioning sequence recovers a bridge offset without which heading would
be tens of degrees out. Future work exercises the
correlated and signal-proportional error terms in a closed-loop case, steps the
consumer on the importer's clock, and measures SIL-to-HIL transfer on physical
STM32H743 hardware.

\section*{Reproducibility}
The framework, the seven sensor FMUs (five sensors, two of them at both
fidelity tiers), the case study, the Renode software-in-the-loop harnesses and
the plotting scripts are open source under GPLv3. Each sensor FMU is exported
for both FMI 2.0 and 3.0 from one source, and every model constructor accepts an
RNG seed---so a run's turn-on biases, hard iron and bridge offset are
reproducible bit for bit, which is what makes a figure like
Fig.~\ref{fig:magerror} checkable rather than merely illustrative. The
reference run of Section~\ref{sec:results} is repository commit
\code{55a95ce} with run seed 17, against the plant FMU of Aetherion 0.16.0;
its configuration files, console transcripts and the script that computes the
statistics quoted there accompany the manuscript source.

Continuous integration rebuilds every tier on each change and runs three
suites: the host-side unit and integration tests over the conversion routines,
frame parsers, error models and simulated buses (36 cases); the packaging checks over the
exported archives described in Section~\ref{sec:discussion} (14 cases, one per
model per FMI version); and the Renode SWIL harness, which drives
cross-compiled firmware under \code{pyrenode3} (3 cases). Line coverage of the
natively compiled framework sources under the first of those suites is
$85.9\%$ at the commit reported here, as measured by \code{gcovr} in
continuous integration and published through Codecov.
